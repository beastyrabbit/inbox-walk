Product outcome

Review events, orders, and incidents instead of notification fragments

The unit of work

One bundle contains the messages that describe a single real-world story. The snapshot contains every matching unread message at the moment the review starts. There is no fixed message-count limit.

development workstream order and delivery incident standalone message

One slide, several sources

A repository slide can combine PR creation, review comments, merge status, deployment attempts, and the latest Railway outcome. An order slide can combine payment, merchant confirmation, carrier handoff, and delivery.

The slide summarizes the current state and shows a short timeline. It does not replace or delete the source messages.

Strong link

Shared order number, tracking number, repository, pull request, commit SHA, deployment ID, service, or an explicit link from one message to the next.

Conflicting evidence

Similar subjects are not enough. Different order numbers, repositories, environments, recipients, or distant time windows keep messages in separate bundles.

Suggested link

When the relationship looks plausible but lacks a hard identifier, the UI can place the messages nearby and ask whether they belong together.

Default cost of uncertainty Create an extra slide. A needless split costs one swipe. A false merge can hide an unrelated problem inside a reassuring summary.

Architecture

An indexed seed-and-retrieve bundler with one mutation boundary

The system first extracts reliable links and builds a searchable graph across the complete snapshot. It then takes one unassigned seed, retrieves plausible companions, and asks Codex to decide membership. A final pass names each story, summarizes its current state, and checks the bundle boundaries. Nothing changes in Fastmail while bundles are built or reviewed.

    3Extract link keysFind repository, commit, service, order, tracking, sender, and time signals.

No fixed inbox limit, no giant prompt Fetch JMAP results page by page until every matching ID belongs to the stable snapshot. Extract hard identifiers locally for each page. Partition only the uncertain relationships into model-sized jobs, then reconcile the complete proposed bundle graph. The final membership check covers every snapshot ID. Internal page sizes control memory and request size, but never truncate the review.

Freeze all IDs safely

Page through Email/query while its query state stays unchanged. If the state changes mid-fetch, restart the query. Once complete, freeze that full ordered ID list as the review snapshot.

Load summaries on demand

Keep the ID list and compact bundle index server-side. Fetch summary pages and the current bundle into the browser as needed. Bodies and attachments remain lazy.

Bundle across page boundaries

Exact keys enter one global relationship index, so page 1 and page 20 can still join. Model jobs handle uncertain edges, not arbitrary page-sized islands.

Finalize in bounded batches

Lock the complete reviewed selection first, then mark its explicit snapshot IDs read in retryable internal batches. Newer mail and context-only IDs stay untouched.

Bundling algorithm

Use the first open email as a seed, but search through an index

Your second idea is the better base. Start with the first unassigned email, retrieve related messages from everything still open, create the bundle, remove its members from the open set, and continue with the next unassigned email. The important change is that retrieval uses a prebuilt index rather than asking Codex to scan the entire remainder every time.

    7Reconcile onceCompare neighboring bundle summaries and shared entities, fix missed joins, then validate every ID exactly once.

What retrieval should use

  • Exact IDs and URLs first.
  • Known repo-to-service and merchant-to-carrier mappings.
  • Shared entities such as item, branch, address fragment, actor, or service.
  • Time windows and subject or preview similarity as broad recall signals, never final proof.

What Codex must not do

  • Search the full mailbox by itself.
  • Create identifiers that did not come from extraction.
  • Remove excluded candidates from future consideration.
  • Make Fastmail mutations while membership is still being built.
Keep candidates broad, membership strict Missing a candidate means Codex never gets a chance to connect it. Retrieval should therefore include doubtful possibilities. The membership judge can reject them, and an excluded candidate stays in the open set for another seed.
Large candidate sets continue in pages A repository or large order may produce more candidates than one model request should contain. Rank candidates, judge a bounded page, update the provisional bundle summary, and continue until every retrieved candidate has a decision. The page size is an internal request limit, not a bundle-size limit.
Keep version one cheap Start with inverted maps for exact identifiers plus SQLite FTS over subjects and previews. Do not add an embedding service yet. The correction data will show whether lexical retrieval misses enough real relationships to justify it.

Learning loop

Learn which messages belong together

What counts as a label

  • You merge two suggested slides.
  • You split an incorrect bundle.
  • You move one message to a different bundle.
  • You confirm a rule such as "this Railway service deploys this GitHub repo".

What must never count

  • The bundler's own proposed relationship.
  • A message becoming read because another client opened it.
  • Two messages arriving close together without another shared signal.
  • A generated repo, service, merchant, or carrier mapping that you have not approved.
1Capture correctionStore the merge, split, or move plus the structured link signals.
2Accumulate evidenceWait for enough examples. One correction does not become a global rule.
3Run learnerCodex proposes a small profile diff with supporting example IDs.
4Replay and scoreTest bundle membership against labeled history and held-out stories.
5Approve versionYou see the rule change and its measured effect before activation.

Preference profile, not model training

Start with a versioned, human-readable linking profile injected into each bundling run. It records trusted mappings, required evidence, and forbidden joins. This is easier to inspect, correct, roll back, and test than fine-tuning. Until the app has hundreds of reliable merge and split labels, a "learning run" should only propose profile changes.

Few-shot limit per Codex call

Include at most two confirmed positive examples and two confirmed negative examples. This means four examples at most, split evenly by outcome. If fewer relevant confirmed examples exist, send fewer. Never fill the quota with generated examples.

  • Positive means the user confirmed that the candidate belongs with the seed.
  • Negative means the user split or rejected the same kind of proposed relationship.
  • Prefer examples from the same provider pair and bundle kind as the current decision.

Examples contain signals, not old mail

Store and inject a compact decision record rather than message bodies. Each example contains the provider pair, extracted identifiers, relevant time gap, accepted or rejected outcome, and a short user-approved reason.

The active linking profile carries stable rules. Few-shot examples only help with the current ambiguous edge and should not grow with history.

Good learning is asymmetric A false merge is worse than an extra slide. Score incorrect joins separately from missed joins and require a much lower false-merge rate.

Rollout

Start with obvious bundles, then learn cross-source relationships

Phase 0

Offline replay

Build GitHub, Railway, Amazon, DHL, and multi-parcel fixtures. Label correct membership and intentional splits.

Gate: every message appears exactly once and false joins fail tests.

Phase 1

Provider bundles

Bundle GitHub messages by repository and pull request, Railway messages by service and deployment, and carrier updates by tracking number.

Gate: manual merge and split controls work without changing Fastmail unexpectedly.

Phase 2

Cross-source bundles

Connect GitHub to Railway and merchants to carriers when identifiers or approved mappings support the relationship.

Gate: false-merge rate stays below the chosen threshold on held-out stories.

Phase 3

Context lookback

Use recent already-read summaries to explain new unread messages, such as a shipment notice for yesterday's order.

Gate: context-only IDs can never enter the JMAP mutation set.

Suggested initial link policy

  • Auto-join on exact tracking number, order number, pull request URL, deployment ID, or commit SHA.
  • Require at least two independent soft signals for a proposed cross-sender link.
  • Never auto-join across conflicting order numbers, repositories, accounts, or environments.
  • Show weak candidates as suggestions rather than bundle members.

Bundle scorecard

  • False joins, where unrelated messages land on one slide.
  • Missed joins, where one story still needs several slides.
  • Split and merge corrections by provider pair.
  • Slide reduction, compared with the raw unread message count.

Data and API

Small additions that fit the current codebase

Server modules

  • snapshot-store.ts freezes the complete paginated JMAP ID manifest and serves bundle pages without a count cap.
  • bundle-index.ts retrieves broad candidate sets from exact-key maps, approved mappings, entities, time, and SQLite FTS over subjects and previews.
  • bundles.ts runs the seed queue, selects at most two positive and two negative examples, validates membership, and starts fresh no-tools Codex sessions.
  • bundle-signals.ts extracts provider, repository, deployment, order, tracking, and time signals.
  • bundle-store.ts stores relationship labels, approved mappings, and profile versions in SQLite.
  • The existing review finalizer remains the only path that marks snapshot IDs read.

Client additions

  • A "Bundle related messages" option before the review starts.
  • A lightweight checkpoint with the opaque snapshot ID, bundle revision, position, and decisions rather than thousands of copied message IDs.
  • One slide per bundle with a generated state summary and timeline.
  • Merge, split, move, inspect, and keep-unread controls.
  • A linking-profile view with approved repo-service and merchant-carrier mappings.

Storage policy

  • Store the complete ordered snapshot ID manifest server-side. Do not truncate it or send the entire manifest to the browser.
  • Keep raw message bodies and attachment content in the existing server snapshot cache only. Do not persist them for relationship learning.
  • Persist message IDs, bundle membership, structured link signals, profile versions, confidence, timestamps, and explicit merge or split labels.
  • Make retained snippets opt-in if later evaluation proves that structured signals are insufficient. Encrypt them and set a retention limit.
  • Keep a short, bounded context lookback of recent summaries or fetch them on demand. Mark every lookback ID as context-only.
  • Delete expired bundle runs and reconcile message IDs that no longer exist.
Stable snapshot rule A bundle may cite an already-read Amazon order as context for an unread DHL notice. Finalization must discard every context-only ID and accept only unread IDs from the explicit snapshot. This keeps the current stable snapshot invariant intact.

The current Codex integration already creates a fresh in-memory session, disables built-in tools and project context, and accepts one schema-constrained submission. Reuse that shape. Official OpenAI documentation also supports schema-constrained output through Structured Outputs in the Responses API, so a later move to the direct API would preserve the same typed contract. Safety and failure modes

Mail is untrusted data, and read-state changes still matter

  1. Prompt injection in email content

    Use no built-in tools, one schema-only result channel, strict delimiters, bounded fields, and server validation. Text inside mail can describe relationships but cannot alter policy or call functions.

  2. Two unrelated stories get merged

    Prefer exact identifiers and approved mappings. Treat semantic similarity and time proximity as suggestions. Conflicting hard keys always force a split.

  3. A summary hides an unresolved problem

    Derive the current state from the last relevant event and preserve warnings. "Merge succeeded" must not override a later production deployment failure.

  4. Self-reinforcing relationships

    Learn only from explicit merge, split, and move labels. Candidate mappings stay inactive until replay evaluation and approval.

  5. Partial or stale snapshot

    Bind every bundle to the snapshot ID. Validate that each snapshot email appears in exactly one bundle and that context-only IDs never become actionable.

  6. Attachments omit important context

    Keep the original message inspectable and flag attachment-bearing events. If attachment content influences a bundle summary, use the existing fail-closed extraction rules.

  7. Provider outage or invalid model output

    Fall back to one slide per email. Leave every message unread until the normal review finalizes it. Never accept partial bundle membership.

Acceptance criteria for the first release

  • The system indexes every summary, and Codex reconciles the complete relationship graph before returning bundles.
  • A snapshot containing more than 250 messages completes without truncation.
  • Every snapshot email belongs to exactly one bundle or the whole run fails.
  • A standalone email becomes a valid one-message bundle.
  • No Codex request contains more than two confirmed positive and two confirmed negative examples.
  • The final reconciliation can merge missed neighbors but cannot silently drop or duplicate an ID.
  • The UI shows current state, link evidence, timeline, originals, and correction controls.
  • Finalization receives only explicit unread snapshot IDs.
  • Automated tests never call live mail or AI providers.

Recommended first milestone

Ship same-provider GitHub and Railway bundles first, with one slide per repository or service story. Add their cross-source mapping next. Then add Amazon and carrier bundles with explicit multi-parcel handling.

This sequence proves the slide interaction before the harder relationship work and collects real merge and split labels.

Decision to lock before coding Completing a bundle should process its unread member messages as one review action. The user can keep any original unread before final confirmation. The app does not need unattended auto-read to remove most of the repetitive work.
This plan evolves Inbox Walk v0.5.2 from a 250-message snapshot to a complete paginated snapshot with no fixed message-count cap. It keeps lazy bodies, explicit finalization, minimal SQLite history, and the existing server-side Codex session. It proposes no send-mail capability and no Railway or GitHub account integration. GitHub, Railway, Amazon, and carrier relationships come from the mail itself and from mappings the user confirms.
